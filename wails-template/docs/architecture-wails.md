# Wailsアーキテクチャ

本書は [architecture.md](architecture.md) のWails固有の構成を補足する。プロダクト固有のシステム構成、実現パターン、データ設計、設計判断は同書に記録し、本書の記述は転記しない。

## 1. 構成と責務

Windows専用のWails v3アプリとし、単一リポジトリ・単一Goモジュールで構成する。フロントエンドはReact・TypeScript・Vite、TanStack Router／Query、Mantine・CSS Modulesを使用する。Routerはファイルベース・ハッシュ履歴とする。

フロントエンドは利用者との対話をユースケース単位で構成し、Goは画面や対話手順に依存しない機能を提供する。ユースケースと機能はn:nで対応し、画面・フック・Serviceとの一対一対応は要求しない。

| 配置 | 責務 |
| --- | --- |
| `main.go` | 依存オブジェクトの生成・接続、Service登録、アプリ起動 |
| `frontend/src/app/` | Provider・Routerの組み立て |
| `frontend/src/routes/` | ルート定義とユースケースの配置。loaderはQueryの事前取得に利用する |
| `frontend/src/usecases/<目的>/` | 対話の進行、入力途中の状態、機能の組み合わせ、専用UI |
| `frontend/src/features/<機能領域>/` | Queryの定義、更新要求、変更イベントの購読 |
| `frontend/src/shared/` | 特定のユースケース・機能アクセスに依存しない共用部品 |
| `internal/<機能領域>/` | 機能Service、業務処理、永続化、外部API・OS操作 |

操作の呼び出しは `usecases → features → 生成バインディング → Goの機能Service` とする。生成されたデータ型の参照は制限しない。`features`は画面・ユースケースへ依存しない。

対話制御はコンポーネントから始め、必要な部分をカスタムフックへ分離する。Goも機能領域内で必要な関数・型へ分け、固定の多層構造は設けない。インターフェイスは具体的な差し替え・検証上の必要性がある境界に限り、依存はコンストラクターで渡す。

## 2. 状態と更新

| 状態 | 管理主体 |
| --- | --- |
| 業務データ・バックグラウンド処理の状態 | Go |
| 取得結果のキャッシュ・取得や更新の実行状態 | TanStack Query |
| 表示対象ID・検索条件などの遷移状態 | TanStack Router |
| 編集下書き・確認段階などの対話状態 | React。複数画面にまたがる場合は対話中に維持される共通親 |

Queryは機能・取得条件ごとに定義し、ユースケース間で共有する。編集下書きは取得データから分離し、再取得で上書きしない。保存失敗時は維持し、完了・中止時に破棄する。

保存成功後は関連Queryの無効化・再取得を基本とする。変更イベントも機能アクセス側で同じ更新経路へ接続し、重複する再取得を抑える。保存成功後の再取得失敗は、保存失敗と区別する。

## 3. 機能の契約と結果の確定

機能ServiceをWailsへ直接登録し、公開メソッドと入出力型はGo側で定義する。TypeScript側は生成バインディング・生成型を利用する。内部型と公開型は、内部実装の都合や機密情報が露出する場合に分離する。

入力と業務上の成立条件はGoで検証する。一体で成立させる更新は一つの公開操作にまとめ、必要なトランザクションをGo内で完結させる。保存成功と変更通知は結果確定後に返す。保存先の変更と、複数保存先の同期は別の機能として扱う。

操作の結果は戻り値・エラー、変更・進捗の通知はWails Eventsを使う。イベントの受信履歴を正本とせず、現在の状態は取得操作で確認できるようにする。画面の終了・購読解除・処理のキャンセルは区別する。

公開エラーは`code`・`message`と、必要時の`fieldErrors`を持ち、Promiseを失敗させる。Goは内部原因を公開情報と分離し、フロントエンドはコードに応じて表示と対話の再開を決める。

## 4. モックと検証境界

仕様合意用モックは画面・対話制御・Queryを本番と共用し、機能呼び出し境界をViteのモジュール参照設定で一箇所から差し替える。契約は生成型と共有し、既定は実処理とする。固定データの移動・削除、テスト作成時点は [モック標準](standards/mock-driven-development.md) に従う。

検証はPlaywrightによる実処理E2Eを中心とする。ブラウザで確認する範囲はWailsのserver buildを使用し、ネイティブ操作と実行環境依存の動作はWindowsの実アプリで確認する。Vitest・React Testing Library・Go標準テストは必要なリスクを補う。

## 5. 実行とデータ保護

単一インスタンス・主ウィンドウ1つを既定とする。リソースとバックグラウンド処理はGoのServiceが所有する。終了前の未保存確認はフロントエンド、安全に停止できるかの判断はGoが担い、終了確定後に停止・解放する。

業務データ・設定・秘密情報の永続化はGo側に置き、アプリ配置先と分離する。秘密情報は通常の設定と分ける。保存形式の変更は明示的な移行で扱い、読込失敗を空データへ置き換えて上書きしない。

本番UIは同梱アセットを使用し、外部コンテンツにアプリの権限を与えない。診断ログはGoの`slog`へ集約し、機密情報を除いて容量制限付きでローカル保存する。

## 6. 配布とアプリ内更新

Goとフロントエンドを一体でビルドし、未署名NSISインストーラーをユーザー単位で導入する。配布元は共有フォルダまたはGitHub Releasesとする。

Goの更新Serviceが更新情報・インストーラーを取得し、更新情報のEd25519署名とインストーラーのハッシュを検証する。利用者の同意と未保存確認後、NSISへ引き渡してアプリを終了する。NSISは終了を待って適用し、成功後に再起動する。更新で利用者データを削除しない。

更新用署名はWindowsのコード署名とは別に扱い、未署名アプリの実行可否は配布先のポリシーで確認する。

<a id="mock-scope"></a>
## 2. モック駆動開発の適用範囲

採用する対象・対象外とその理由: {{MOCK_SCOPE}}

初期案は、画面のレイアウト、操作フロー、表示状態など、動作を見て仕様を合わせる必要がある新規機能・仕様変更を対象とします。画面のないプロジェクトでも、入出力や対話の認識合わせが必要なら、その境界を指定して適用できます。画面の追加は不要です。

既に合意した仕様のバグ修正、振る舞いを変えない内部変更、文書のみの変更には、仕様合意のためのモック作成を要求しません。テストで外部依存を置き換えるかどうかは、別途その検証の必要性で判断します。

対象がなければ理由を記録します。ツールの採否は適用プロセスと分け、必要な段階で [プロジェクト定義](project.md#design) に記録します。

<a id="sources"></a>
## 3. 文書の役割と分割

| 正本 | 扱う内容 |
| --- | --- |
| 本書 | 標準の採用と適用、配置、保護する合意 |
| `standards/` の各標準 | プロジェクトに依存しない実施規則 |
| [project.md](project.md) | 製品の目的・制約、機能仕様、外部仕様の事実、設計判断、実行手順、検証結果 |
| [PLAN.md](../PLAN.md) | 状況、作業順序、未決・未実装・未検証事項 |
| [README.md](../README.md) | 概要と参照案内 |
| [AGENTS.md](../AGENTS.md) | エージェント作業時の参照マッピング |

仕様の独立利用、異なる更新頻度、参照のしにくさなど、分割の必要が生じた場合だけ正本を分けます。移した内容を元の文書に残さず、参照に置き換え、本表と関連リンクを更新します。用語集は解釈のずれが生じた用語、設計判断記録は標準の作成条件を満たす判断だけを扱います。

図の形式や枚数、文書の章数は固定しません。プロジェクトで必須にする資料・視点がある場合は、目的と対象をこの節に記録します。

<a id="agreements"></a>
## 4. 保護する合意

採用した規則と適用範囲、正本の責務、プロジェクト定義に記録した合意済みの要件・制約・期待結果・完了条件を保護します。本節も含め、変更は [標準の変更手続き](standards/design-and-documentation.md#agreement-changes) に従います。

導入前の記入欄、検討案、モックの仮定を合意済みとみなしません。未決事項の詳細と状態は [PLAN.md](../PLAN.md) に記録します。

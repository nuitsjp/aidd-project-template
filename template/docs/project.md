## 3. ユースケースと合意

ユースケースは、1人の主アクターの1つの目的に対応し、主成功系列を1本だけ持つ単位で切ります。API、画面、データ取得の単位では切りません。主成功系列のステップに「〜の場合」の条件分岐を書かず、条件で結果が変わるなら拡張に書きます。拡張は主成功系列の途中から分岐し、単独では目的を達成しないものに限り、単独で達成できる系列は別のユースケースにします。拡張が3本必要になったらユースケースを分割します。

## 4. 確認した事実とユースケース固有の設計

{{FACTS_AND_LOCAL_DESIGN}}

- **確認した事実**: 外部仕様や既存コードの調査結果（情報源・対象版・確認日・確認範囲）。仮定と明確に区別します。外部システムの実測応答を保存する場合は `reference/` に置き、ここから参照します。
- **技術選定**: 言語・ライブラリ・モック機構の選定理由と、追加する仕組みに対する [判断基準](standards/design-and-documentation.md#design-decisions) の根拠。
- **パターンからの逸脱**: 参照する実現パターンと異なる点だけを書きます。責務と境界の本体は [アーキテクチャ](architecture.md) に置きます。

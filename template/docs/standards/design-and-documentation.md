# 設計・文書作成の標準

標準 ID: `project-template-design-and-documentation` / 版: **2**

<a id="implementation-principles"></a>
## 1. 適用原則

現在の要件を満たす最小限かつ最も単純な構成から着手します。単純さとは、コード行数やファイル数だけでなく、理解・実装・変更・検証・運用の総負担の少なさで判断します。既存機能の活用、ライブラリ導入、独自実装を同一基準で比較し、文書も実装も必要なもののみを追加します。

- 依頼範囲外の機能追加、無関係なリファクタリング、汎用化を目的とした過剰な共通基盤を作らない。
- 後方互換性やフォールバックは、明示的な要件がある場合のみ実装する（失敗を隠蔽する代替値を勝手に補わない）。
- 性能改善は計測結果に基づき、問題の箇所に限定する（推測に基づく先行対策を行わない）。
- 入力検証はシステム境界（ユーザー入力・外部連携等）で行い、内部での不要な重複検査や防御的実装を増やさない。
- テストは期待される振る舞いと実際のリスクを検証する（実装のなぞりや形式的な網羅率稼ぎを避ける）。

<a id="design-decisions"></a>
## 2. オーバーエンジニアリングの抑止

新しい層、抽象化、依存ライブラリ、外部サービス、運用機構を追加する場合は、以下を説明できることを条件とします。

1. 現在の要件や確認済みリスクの何に対応するか。
2. 導入しない場合、具体的にどのような問題が生じるか。
3. 局所的な修正、より単純な構成、手動運用ではなぜ不十分か。
4. なぜ今必要であり、導入・保守・運用の負担を受け入れられるか。

合意された将来要件であっても、今実装する必要性は個別に判断します。根拠が不十分な場合は計画への記録にとどめ、実装を見送ります。

<a id="document-roles"></a>
## 3. オーバードキュメンテーションの抑止

決定事項ごとの正本は1箇所に集約し、仕様の重複記述を排除します。

- **新設・分割の基準**: 「誰が何を判断するために読むか」「既存正本への追記ではなぜ不十分か」を説明できる場合のみ新設します。コードから自明な内容の逐語説明や、他文書の転記は不要です。
- **記入欄の取捨選択**: 今回の判断に必要な項目のみを使用し、非該当の項目は削除できます（非該当の理由が重要な場合のみ記録します）。推測で未決事項を水増ししてはなりません。
- **必要な情報の維持**: 要求、根拠、責務、障害時の動作、検証条件など、実装や受け入れの判断に必要な情報は省略しません。

| 情報の種類 | 記録するもの |
| --- | --- |
| 事実 | 情報源、対象版、確認範囲（仮定と明確に区別する） |
| 合意 | 決定内容、範囲、判断者、日付、根拠 |
| 実装 | 対象コードと仕様との対応（コードの存在自体は合意や検証を意味しない） |
| 検証 | 実行条件、対象版、結果、証拠（未検証の項目を合格扱いにしない） |

未決事項は一意な ID、前提、影響範囲、解消条件で追跡します。旧文書や旧実装は過去の証跡とし、現行仕様へ自動的に持ち越しません。

<a id="architecture-method"></a>
## 4. 必要な設計の具体化

1. 対象機能の入力、期待結果、外部仕様の事実を確認する。
2. システム・実行・保存・信頼境界と責務を整理する。
3. 主要なシナリオから、状態更新の担当、結果確定点、障害時の停止・継続範囲を明確にする（競合や通信断がある場合はトランザクション境界も定義）。
4. 追加する仕組みの根拠と検証方法を定め、受け入れ条件と照合する。

図法や章構成は固定しません。文章や表で十分ならそれを使い、構造や時系列の理解が難しい場合のみ図を追加します。プロジェクト固有で必須と合意された資料がある場合はその指定に従います。

<a id="completion"></a>
## 5. 判断の記録と完了基準

設計判断の理由は該当箇所の近くに簡潔に記録します。ADR（設計判断記録）は「変更負担が大きい」「理由が非自明」「重要なトレードオフがある」のすべてを満たす場合のみ作成します。

- **設計の完了条件**: 主要シナリオについて、データの同一性、状態更新の主体、結果確定点、障害時の停止・継続範囲、および検証方法が明確になった時点で設計完了とします。
- **機能の完了条件**: 合意範囲の実装、必要なテストおよび実環境検証の合格、必須修正の解消が必要です。文書作成、モック合意、コードの存在だけでは完了とはみなしません。
- **レビュー指摘の分類**: 指摘は「必須修正（要件充足に必須）」「任意改善（完了を妨げない）」「対象外」に分類します。必須の修正が残る場合は未完了とし、合意済みのリスク受容事項を根拠なく再審議しません。

<a id="agreement-changes"></a>
## 6. 合意を保護する変更手続き

1. 着手前に、採用規則、正本の責務、保護する合意、依頼範囲を確認する。
2. 合意済みの要件・制約・仕様を変更・緩和する場合は、変更内容・理由・影響を明示し、合意を得てから適用する（表現の改善や既に承認済みの変更に再承認は不要）。
3. 完了前に、着手時の合意との差分、検証結果、正本間のリンク整合性を確認する。

変更の検討や調査は先行して進め、確認が必要な判断事項のみを具体的に提示してください。

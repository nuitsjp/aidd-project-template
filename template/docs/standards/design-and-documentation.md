# 設計・文書作成の標準

標準 ID: `project-template-design-and-documentation` / 版: **1**

## 1. 適用原則

現在の要件を満たす最も単純な構成から始めます。文書も実装も、理解・変更・検証・運用に必要なものだけを増やします。製品固有の制約、採用構成、標準との差分はプロジェクト側の正本に記録します。

<a id="design-decisions"></a>
## 2. オーバーエンジニアリングを抑える

新しい層、抽象化、依存ライブラリ、サービス、運用機構などを追加する場合は、次の4点を説明できることを条件とします。

1. 現在の要件・確認したリスク、または合意済みの将来要件の何に対応するか。
2. 導入しなければ、具体的にどの問題が生じるか。
3. 局所的な修正、より単純な構成、許容された手動運用ではなぜ不十分か。
4. なぜ今必要で、導入・保守・学習・運用の負担を受け入れられるか。

将来要件が合意されていても、今実装する必要性は別に判断します。根拠がなければ追加を見送り、必要なら計画に残します。

- 依頼外の機能、無関係なリファクタリング、一度しか使わない処理の汎用基盤を追加しない。
- 後方互換性やフォールバックは、明示された要件がある場合だけ実装する。失敗を成功に見せる代替値を勝手に補わない。
- 性能改善は目標と計測に基づき、問題の箇所に限定する。仮想的な負荷への先行対策をしない。
- 入力検証はユーザー入力・外部連携などのシステム境界で行い、成立しない状態のための防御処理や同じ検査の重複を増やさない。
- テストは期待する振る舞いと現実のリスクを検証する。実装をなぞるだけのテストや、形式的な件数稼ぎをしない。

<a id="document-roles"></a>
## 3. オーバードキュメンテーションを抑える

決定事項ごとの正本は1箇所にします。入口文書は概要とリンク、計画書は状況と未決事項を扱い、確定した仕様を複製しません。

文書を新設・分割する前に、「誰が何を判断するために読むか」「既存の正本への追記や参照ではなぜ足りないか」を確認します。説明できなければ新設しません。空の章、全項目を埋めるだけの様式、コードから明らかな内容の逐語的な説明、同じ規則の転記は不要です。

一方、要求、根拠、責務、失敗時の動作、検証条件など、実装や受け入れの判断に必要な情報は省略しません。短さだけを目的に意味や保護する合意を失わせません。

| 情報の種類 | 記録するもの |
| --- | --- |
| 事実 | 情報源、対象版、確認した範囲。仮定と区別する |
| 合意 | 決定内容、範囲、判断者、日付、根拠 |
| 実装 | 対象コードと仕様との対応。存在だけでは合意や検証を意味しない |
| 検証 | 実行条件、対象版、結果、証拠。未検証を合格にしない |

未決事項は一意な ID、前提、影響・依存範囲、解消条件で追跡します。依存する設計は未完了とし、独立した作業は進めます。旧文書や旧実装は証跡として扱い、現行仕様へ自動的に採用しません。文書の移動・分割時は正本の対応表と参照を更新します。

<a id="architecture-method"></a>
## 4. 必要な設計を具体化する

1. 対象機能の入力、期待結果、外部仕様の事実を確認する。
2. 関係するシステム・実行・保存・信頼境界と責務を整理する。
3. 重要な正常・異常シナリオから、識別、状態の更新担当、結果確定、失敗時の範囲を定める。該当する競合・通信断・障害・復旧を確認し、並行制御や永続化のトランザクション境界も具体化する。
4. 追加する仕組みの根拠と検証方法を決め、製品の制約・受け入れ条件と照合する。

構成や図法は固定しません。文章や表で十分ならそれを使い、境界・依存・時系列が読み取りにくい場合に図を追加します。C4 の必要な視点や arc42 の関連項目を利用しても、形式を満たすためだけに図や章を増やしません。プロジェクトで合意した必須資料がある場合は、その要求に従います。

<a id="completion"></a>
## 5. 判断の記録と完了基準

判断理由は該当する設計箇所へ簡潔に記録します。ADR（Architecture Decision Record）は「変更負担が大きい」「理由が自明でない」「実際の選択肢とトレードオフがある」のすべてを満たし、独立して記録する必要がある場合に作成します。

設計は、対象の重要シナリオについて次の観点を説明し、期待結果の検証方法が具体化された時点で完了です。適用しない観点は、その理由を明示します。

- 何を同一と判定し、どの情報を対応付けるか。
- 誰がどの状態を更新するか。
- いつ結果が確定し、利用者や連携先が何を観測するか。
- 失敗時に何が残り、何を停止・継続するか。
- 期待結果をどの条件・方法で検証するか。

機能の完了には、合意した範囲の実装、必要なテスト・実環境での検証の合格、残る必須修正の解消が必要です。文書作成、モック合意、コードの存在は、それぞれ単独では機能の完了を意味しません。

レビュー指摘は、合意した要件・受け入れ条件を満たすための「必須修正」、完了を妨げない「任意改善」、範囲に含まれない「対象外」に分けます。必須の検証や修正が残れば未完了とし、合意済みのリスク受容事項を根拠なく再審議しません。

<a id="agreement-changes"></a>
## 6. 合意を保護する変更手続き

1. 着手前に、採用版、適用範囲、正本の責務、保護する合意、依頼された変更範囲を確認する。
2. 合意済みの要件・制約・必須事項・完了基準を変更・削除・緩和する場合は、変更前後、理由、影響を具体化し、明示的な合意を得てから適用する。既に許可された変更や、意味を変えない表現改善には再承認を求めない。
3. 完了前に、着手時の合意と差分を照合し、必須事項の欠落、未決・未検証の誤った完了扱い、正本の重複やリンク切れを確認する。

この手続き自体と適用範囲の変更も対象です。変更内容の検討や影響調査は先に進め、確認が必要な判断だけを具体的に提示します。

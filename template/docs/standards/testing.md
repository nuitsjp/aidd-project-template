# テストの標準

標準 ID: `project-template-testing`

## 1. 目的と適用

テストは、文書で合意した要件と設計を、変更後も実処理が満たし続けることを確認するために作成します。各テストは根拠となる文書の特定の記述へたどれるものとし、根拠をたどれないテストや、網羅率の達成・実装の形式的追認を目的としたテストは作成しません。

追加・更新の時点は [モック標準の実施手順](mock-driven-development.md#workflow) に従います。モック標準の対象外の作業（確定済み仕様の不具合修正、内部変更）では、実装と同時に必要なテストを追加・更新して合格を維持します。検証レベルごとの手段・ツール・配置・実行コマンド、分離の仕組み、実行構成が複数ある場合に各構成で実行するテストは、技術固有のアーキテクチャ文書（なければ [アーキテクチャ](../architecture.md)）に記載し、本標準の規則は再掲しません。

<a id="sources"></a>
## 2. 根拠

| 根拠 | 正本 |
| --- | --- |
| 機能要件 | ユースケースとシナリオ（分岐条件、条件ごとのメッセージ、受け入れ条件、共通の受け入れ条件） |
| 非機能要件 | [プロジェクト定義](../project.md) 第2節と [アーキテクチャ](../architecture.md) 第4節の制約 |
| 設計 | アーキテクチャ、`design/UCP-n.md`、`design/data.dbml` で定めた責務と約束（公開境界の契約、結果確定点、障害時の停止・継続） |

<a id="levels"></a>
## 3. 検証レベル

| レベル | 範囲 | 作成する対象 |
| --- | --- | --- |
| システム全体 | 利用者の入口から結果確定までを実処理で通す（E2E） | シナリオテスト（必須）と、実行構成全体でのみ確認できる非機能要件 |
| 公開境界 | アーキテクチャ第2節で公開境界とした関係線の入口へ、UI を経由せずに入力する | 公開境界に届き、UI からは再現できない入力に関する要件と設計 |
| 部品 | 単一の責務を持つ部品 | システム全体で検証しにくいリスク（並列、境界値、障害時動作、非同期の競合、組み合わせの多い分岐） |

呼び出し側と提供側の型・形の一致は、契約からの生成、生成物の一致検査、型検査で保証し、テストで重複して確認しません。

<a id="scenario-tests"></a>
## 4. シナリオテスト

- シナリオテストは `<ユースケース名>/<シナリオ名>.<拡張子>` の1ファイルに置き、`開始条件`（拡張は `分岐条件`）、手順表の各行に対応する `手順1`〜`手順N`、`受け入れ条件` をラベルとする区切りで記述します。
- 各手順の区切りでアクターの操作とシステムの振る舞いを検証し、共通の受け入れ条件は該当シナリオの `受け入れ条件` で検証します。保存結果は UI と確定済みデータの両方で確認します。
- UI から再現できない入力に関する受け入れ条件は、公開境界のテストで確認します。
- シナリオに記載のない振る舞いは、拡張シナリオとして合意・文書化してから検証を追加します。

<a id="boundary-and-component-tests"></a>
## 5. 公開境界と部品のテスト

- 公開境界のテストは、宣言した公開境界ごとに作成します。形式違反、他者のデータの指定、認証情報や送信元の不備、上限超過などについて、受け入れと拒否、エラーの形式、拒否時にデータを変更しないことを確認します。
- 部品のテストは、第3節のリスクがある場合に限り作成し、確認するリスクをテスト名で示します。

<a id="isolation"></a>
## 6. テストの分離

- テストごとにデータの保存先と実行状態を持ち、他のテストや実行順に依存しません。
- 共有データの一括削除、テスト用の初期化 API、外側のトランザクションによる巻き戻しは使用しません。
- 同じデータに対する競合は、1件のテスト内で複数の対話を動かして確認します。
- 保存結果は、操作に使った経路とは別の経路（読取専用の接続など）から確定済みのデータを読んで確認します。

# モック駆動開発の標準

標準 ID: `project-template-mock-driven-development` / 版: **2**

## 1. 目的と適用

最小限の動作するモックで操作・入出力・状態の認識を合わせ、合意した仕様を実処理へ接続します。適用範囲はプロジェクトの [文書方針](document-policy.md#mock-scope) で定めます。特定の画面技術やツールは強制しません。

仕様合意のためのモックと、テスト用のスタブ・モックは目的が異なります。テスト用モックの存在をもって仕様合意とはみなしません。

<a id="workflow"></a>
## 2. 機能ごとの実施手順

| 順序 | 実施内容 | 次へ進める条件 |
| --- | --- | --- |
| 1. シナリオを定義する | 仕様の正本に ID、初期条件・入力、操作・契機、期待結果を記入。確認済みの事実と仮定を分け、未決事項は計画書の課題 ID と紐付ける | 確認したい論点とモックで再現する範囲を説明できる |
| 2. 最小のモックを作る | 本番画面・入出力処理を共用し、未実装の外部依存など必要な境界のみ固定データ等に置き換える。状態再現手順を用意する | 同一シナリオを同一条件で繰り返し確認できる |
| 3. 動作で合意する | 再現手順、対象版、シナリオ、判断事項、モック外の範囲を提示し、仕様の正本へ合意を記録する | 実装へ進める範囲が明示的に合意されている |
| 4. 実処理へ接続する | 合意した入出力処理を維持し、境界を実処理へ接続する。モックを無効化した環境で同一の期待結果を確認する | 実際の接続先・処理が使われ、モックへのフォールバックがないことを確認できる |
| 5. 必要な検証を終える | シナリオに対応するテストと、モックで代替できない実環境検証（外部連携、保存、権限、障害等）を実施・記録する | 受け入れ条件を満たし、必須の修正が完了している |

- **合意済みの仕様**: 既に仕様が確定している場合は、モック作成を省略して実装へ進めます。
- **合意の基準**: 実際に動作する状態を提示して合意を得ます（暗黙の了解やモック作成のみを合意とはみなしません）。未合意の仕様に依存する実装は行わず、先行可能な調査や独立した機能を進めます。
- **技術検証の先行**: 外部連携や権限等の実現性が仕様合意を左右する場合は、最小限の実接続検証を先行して実施できます。
- **期待結果の変更**: 合意済みの内容を変更する場合は、理由と影響を提示して再合意します。

<a id="boundaries"></a>
## 3. モックを作り込みすぎない

- 合意に必要な状態と遷移のみを再現し、業務ロジックや永続化処理をモック側に再実装しない。
- 本番用と別系統の画面や専用の通信層を作らず、固定データや既存の仕組みを活用する。
- モックデータは本番の型・契約に合わせて一元管理し、整合性検証には既存の型チェック等の最も単純な手段を用いる（専用基盤を作らない）。
- 新しいモックツールを採用する場合は、導入理由と保守負担を評価し、プロジェクト定義に記録する（ツールの導入自体を自己目的にしない）。
- 本番構成ではモックを無効化する。実処理の失敗をモックの応答でフォールバックしてはならない。

## 4. 記録と実装への引き継ぎ

モック専用の仕様書や台帳は新設せず、既存の正本で内容を管理します。

| 正本の記載箇所 | 記録内容 |
| --- | --- |
| 機能仕様 | シナリオ、期待結果、確認したモックの資産と版、合意内容（判断者・日付・根拠） |
| 設計・実行手順 | モック境界とデータの配置、起動・状態再現・終了・実処理への切り替え手順 |
| 検証結果 | シナリオに対応する実装・テスト、対象環境と版、モック確認および実処理検証の結果・証跡 |
| 作業計画 | 未決事項、依存範囲、未実装・未検証の状態と解消条件 |

モックでの合意は、実処理の正しさ（保存・認証・性能・耐障害性）を保証しません。必要な検証は実環境・実処理で実施し、未検証の機能を完了扱いにしてはなりません。不要になったモック資産は整理し、回帰テスト等に有用なもののみ保持します。

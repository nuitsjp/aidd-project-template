# モック駆動開発の標準

標準 ID: `project-template-mock-driven-development` / 版: **5**

## 1. 目的と適用

最小限の動作するモックで操作・入出力・状態の認識を合わせ、合意した仕様を実現パターンに沿って実処理へ接続します。適用範囲は [文書方針](../document-policy.md#mock-scope) に従います。特定の画面技術やツールは強制しません。

仕様合意のためのモックとテスト用のスタブ・モックは目的が異なり、テスト用モックの存在をもって仕様合意とはみなしません。

<a id="workflow"></a>
## 2. ユースケースごとの実施手順

| 段階 | 実施内容（要約） | 次へ進める条件 |
| --- | --- | --- |
| 1. 仕様作成 | ユースケース本文（主アクター、目的、主成功系列、拡張、受け入れ条件）を作成し、実現パターンを割り当てる（初利用のパターンは本体を記述） | 系列 ID が付与され、モック再現範囲が主成功系列と人が指定した最大2本の拡張に定まっている |
| 2. モック作成 | 本番の型・契約を共有する合成点1箇所で固定データに差し替え、状態 ID ごとの再現手順を用意する | 主成功系列と指定された拡張を同一状態 ID で繰り返し再現できる（失敗分岐・再試行・部分成功は再現しない） |
| 3. 動作合意 | 起動手順、提示コミット、系列・状態 ID、合成点と再利用する本番の型、判断論点（最大3件、各1行、既定案付き）、対象外、返答様式を提示して停止する | 合意記録の4項目（提示コミットのハッシュ、合意した系列 ID、論点ごとの回答、利用者の応答の原文引用）がすべてユースケース本文に記録されている |
| 4. 実処理接続 | 合意した入出力を維持し、パターンの境界を実処理へ接続する。固定データは外部システム境界側のモックへ移すか削除する | モック無効構成で同一系列が同一結果となり、フォールバックがない。役割表の実装パスが記録されている |
| 5. 検証完了 | 系列に対応するテストと実環境検証を実施し、合否表と PLAN.md を更新してコミットする | 受け入れ条件を満たし、必須修正が解消している |

返答様式は「各論点に『既定でよい』または『変更: …』と1行で回答し、末尾に『合意』または『差し戻し』」とします（段階3は反復中の唯一の必須確認点）。

- **仕掛かり上限**: 段階1〜3は保留を含め同時1件、段階4〜5も同時1件です。UC-1 は段階5まで完了してから次へ着手します（UC-1 の段階4は、経路上のコンテナが実処理で接続され、ビルドとテストを1コマンドで再実行できることで完了）。CI があれば同一コマンドを CI でも実行し、資格情報や実機 GUI を要する検証は手元で実行して1行の証跡を残します。
- **合意待ち中の作業**: 当該ユースケースの段階4のうち UI・系列・状態に依存しない部分（外部接続の実装・単体テスト、外部仕様の実測）および PLAN.md の未決事項の解消に限られます。状態語は進めず、他のユースケースには着手しません。合意で系列が変更された場合は UI 側のみ再作成します。
- **範囲の上限**: 拡張系列が3本以上モック化を要する場合は、別ユースケースに分割します。
- **合意済みの仕様**: 既に仕様が確定している場合は、モック作成を省略して段階4へ進めます。
- **仕様変更**: 合意済みの内容を変更する場合は、理由と影響を提示して再合意を得て、提示コミットを更新します。

<a id="boundaries"></a>
## 3. モックを作り込みすぎない

- 置き換え境界は、本番の型・契約を共有できる反復が最も速い合成点1箇所とします（UI 側でも可。当該境界に実処理があればそれを利用）。
- モック専用の型・画面・通信層は作成しません。固定データは算術生成や業務ロジック・永続化の再実装を伴わない固定表とし、本番の型で管理します。
- 合成点の固定データは段階4完了時に外部システム境界側へ移すか削除し、重複保持しません。
- 本番構成ではモックを無効化し、実処理失敗時のモックへのフォールバックは禁止します（切り替えは合成点1箇所、既定は実処理）。
- モックツールの選定は素朴なモックで不足すると判明した時点で行い、事前の比較文書は作成しません（採用時は理由と保守負担を [プロジェクト定義](../project.md#design) に記録）。

## 4. 記録先

モック専用の仕様書は新設せず、既存の正本で管理します。

| 正本 | 記録内容 |
| --- | --- |
| プロジェクト定義 第3節 | ユースケース、系列 ID、合意記録の4項目 |
| アーキテクチャ 第3節 | パターンごとのモック境界と合成点、役割と実装パス |
| プロジェクト定義 第5節 | 起動・状態再現・終了・実処理への切り替え手順 |
| プロジェクト定義 第6節 | 系列と構成ごとの合否 |
| PLAN.md | 状態語、合意版、保留理由、未決事項 |

モックでの合意は実処理の正常動作（保存・認証・性能・耐障害性など）を保証しません。必要な検証は実環境・実処理で実施し、未検証のユースケースを完了扱いにはしません。

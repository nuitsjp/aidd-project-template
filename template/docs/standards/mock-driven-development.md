# モック駆動開発の標準

標準 ID: `project-template-mock-driven-development` / 版: **10**

## 1. 目的と適用

最小限の動作するモックで操作・入出力・状態の認識を合わせ、合意した仕様を実現パターンに沿って実処理へ接続します。適用範囲は [文書方針](../document-policy.md#mock-scope) に従います。特定の画面技術やツールは強制しません。

仕様合意のためのモックとテスト用のスタブ・モックは目的が異なり、テスト用モックの存在をもって仕様合意とはみなしません。

<a id="workflow"></a>
## 2. 系列ごとの実施手順

| 段階 | 実施内容（要約） | 次へ進める条件 |
| --- | --- | --- |
| 1. 仕様検討・記録 | 対象系列の案の全文をメッセージで提示して停止し、議論する（初回は主アクター、目的、前提、主成功系列、受け入れ条件と実現パターンの割り当て。初利用のパターンの案も含む。2回目以降は拡張1本）。利用者の確認後に保存する | 系列 ID、案の全文と UI 確認の要否について議論が完了し、利用者が明示的に確認した内容だけを保存している |
| 2. モック作成 | 本番の型・契約を共有する合成点1箇所で固定データに差し替え、再現手順を用意する | UI 確認が要の対象系列を、提示コミットから同じ固定データで繰り返し再現できる（失敗分岐・再試行・部分成功は、UI の振る舞いを決める必要がある場合のみ要とする） |
| 3. 動作合意 | 起動手順、提示コミット、対象系列 ID、合成点と再利用する本番の型、判断論点（最大3件、各1行、既定案付き）、対象外、返答様式を提示して停止する | 合意記録の4項目（系列 ID、提示コミットのハッシュ、論点ごとの回答、利用者の応答の原文引用）が対象系列について記録されている |
| 4. 実処理接続 | 開始前に、必要なテーブル設計の合意を得る。合意した入出力を維持し、パターンの境界を実処理へ接続する。固定データは外部システム境界側のモックへ移すか削除する | モック無効構成で対象系列が同一結果となり、フォールバックがない。役割表の実装パスが記録されている |
| 5. 検証完了 | 対象系列のテストと実環境検証を実施し、合否表を更新してコミットする。結果を提示して停止する | 対象系列の受け入れ条件を満たし、必須修正が解消し、利用者が完了を確認している |

返答様式は「各論点に『既定でよい』または『変更: …』と1行で回答し、末尾に『合意』または『差し戻し』」とします（必須の確認点は段階1・3・5と、テーブルの追加・変更がある場合の段階4開始前です。差し戻しの際は指示された段階へ戻ります）。

<a id="discussion"></a>
### ユースケース案の提示と保存

1. 検討依頼では、対象範囲で検討した案の全文と未確定の論点を応答の本文に提示し、そのターンを終了して応答を待ちます。要約・差分・ファイルへのリンクだけの提示では代替できません。
2. 議論中はファイルに書き込まず、修正を反映した案の全文をメッセージで再提示します。最新の案に対する利用者の明示的な確認を議論の完了とし、質問・修正指示・無応答を確認済みと扱いません。
3. 確認後に、その内容だけを `docs/usecases/UC-n.md` と必要な一覧・関連設計へ保存します。確認前の新規作成・既存ファイル更新・下書きのファイル保存は禁止します。ユースケース一覧だけの検討や合意済み仕様の変更にも同じ順序を適用します。

- **セッションと仕掛かり上限**: 1回のセッションで1本の系列を段階1から段階5まで通し、完了するまで次の系列と他のユースケースには着手しません。セッションをまたぐ計画は立てず、着手状況は合意記録と合否表から判断します（UC-1-M の段階4は、経路上のコンテナが実処理で接続され、ビルドとテストを1コマンドで再実行できることで完了）。CI があれば同一コマンドを CI でも実行し、資格情報や実機 GUI を要する検証は手元で実行して1行の証跡を残します。
- **ユースケースの完了**: 記述済みの全系列が段階5を終え、追加する拡張がないことを段階5の確認で合意した時点です。
- **合意待ち中の作業**: 段階1の議論中は読み取り調査と案の提示・確認にとどめます。段階3の合意待ち中に段階4に備える作業として、当該系列の UI・系列と未合意のテーブル設計に依存しない部分（外部接続の実装・単体テスト、外部仕様の実測）に限って進められます。未合意のテーブル設計に依存する保存処理やマイグレーションは実装しません。段階は進めず、他の系列・ユースケースには着手しません。合意で内容が変わった場合は、影響する箇所を修正します。
- **モック対象の絞り込み**: UI で確認する系列は、利用者の操作・入出力・状態の振る舞いを動かして仕様を決める必要があるものに限ります。条件とメッセージだけが異なる系列は、条件と対応するメッセージを仕様に定めれば足り、個別の再現は不要です。拡張の本数を理由にユースケースを分割しません。
- **テーブル設計の合意**: 段階3の動作合意後、対象系列で追加・変更するテーブルの設計を [設計標準第4節](design-and-documentation.md#architecture-method) に従って提示し、停止します。[アーキテクチャ第5節](../architecture.md#tables) に合意を記録するまで段階4には進みません。テーブル設計に変更がなければ再合意は不要です。
- **UI 確認が不要な系列**: 段階2・3を省略します。段階1のメッセージでの確認後、確認済みの本文を保存してコミットし、そのハッシュを「提示コミット」欄に記録して論点と回答・利用者の応答の原文を添えます。この場合の提示コミットは確認後の保存内容を特定するものであり、確認前には作成しません。必要なテーブル設計の合意を得てから段階4へ進みます。モックの省略は、必要な仕様合意・実装・検証の省略を意味しません。
- **仕様変更**: 合意済みの内容を変更する場合は、理由と影響を案の全文とともにメッセージで提示し、再合意後にファイルへ反映します。動作合意が必要な系列は段階3、UI 確認が不要な系列は確認後の保存時点で提示コミットを更新します。

<a id="boundaries"></a>
## 3. モックを作り込みすぎない

- 置き換え境界は、本番の型・契約を共有できる反復が最も速い合成点1箇所とします（UI 側でも可。当該境界に実処理があればそれを利用）。
- モック専用の型・画面・通信層は作成しません。固定データは算術生成や業務ロジック・永続化の再実装を伴わない固定表とし、本番の型で管理します。
- 合成点の固定データは段階4完了時に外部システム境界側へ移すか削除し、重複保持しません。
- 本番構成ではモックを無効化し、実処理失敗時のモックへのフォールバックは禁止します（切り替えは合成点1箇所、既定は実処理）。
- モックツールの選定は素朴なモックで不足すると判明した時点で行い、事前の比較文書は作成しません（採用時は理由と保守負担を [プロジェクト定義](../project.md#design) に記録）。

## 4. 記録先

モック専用の仕様書は新設せず、既存の正本で管理します。

| 正本 | 記録内容 |
| --- | --- |
| `docs/usecases/UC-n.md`（[一覧](../project.md#usecases) から参照） | ユースケース、系列 ID、系列ごとの UI 確認の要否と合意記録 |
| アーキテクチャ 第3節 | パターンごとのモック境界と合成点、役割と実装パス |
| アーキテクチャ 第5節 | 対象系列で追加・変更するテーブルの設計と合意記録 |
| プロジェクト定義 第5節 | 起動・終了・モック有効/無効の確認・実処理への切り替え手順 |
| プロジェクト定義 第6節 | 系列と構成ごとの合否 |

モックでの合意は実処理の正常動作（保存・認証・性能・耐障害性など）を保証しません。必要な検証は実環境・実処理で実施し、未検証のユースケースを完了扱いにはしません。

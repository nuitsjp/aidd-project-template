# モック駆動開発の標準

標準 ID: `project-template-mock-driven-development` / 版: **1**

## 1. 目的と適用

最小限の動作するモックで操作・入出力・状態の認識を合わせ、合意した仕様を実処理へ接続します。対象となる変更範囲は各プロジェクトの文書方針で定めます。特定の画面技術、通信方式、モック製品は要求しません。

仕様を合意するためのモックと、テストで依存先を置き換えるモックは目的が異なります。テスト用モックがあるだけで仕様合意が成立したとはみなしません。

<a id="workflow"></a>
## 2. 機能ごとの実施手順

| 順序 | 実施内容 | 次へ進める条件 |
| --- | --- | --- |
| 1. シナリオを定義する | 仕様の正本に ID、初期条件・入力、操作・契機、期待結果、必要な失敗時の状態を記す。確認した外部仕様とモック上の仮定を分け、未決・未合意事項は影響範囲と解消条件を記した計画書の課題 ID に対応付ける | 確かめたい判断と、モックで再現する範囲を説明できる |
| 2. 最小のモックを作る | 本番で使う画面や入出力の処理を共用し、未実装の接続先・外部依存など必要な境界だけを固定データ等に置き換える。状態の選択・初期化手順を用意する | 同じシナリオを同じ条件で繰り返し確認できる |
| 3. 動作で合意する | 確認方法、対象版、シナリオ、判断してほしい点、モックでは確認できない範囲を提示し、仕様の正本へ合意を記録する | 実装へ進める範囲が明示的に合意されている |
| 4. 実処理へ接続する | 合意した画面・入出力の処理を維持し、対象境界を実処理へ接続する。モックを無効にした構成で同じ期待結果を確認する | 実際の接続先・処理が使われ、モックへの自動切り替えがないことを確認できる |
| 5. 必要な検証を終える | シナリオに対応するテストと、モックで代替できない実連携・保存・権限・障害等の必要な検証を実施する。結果と未検証範囲を記録する | 製品側の受け入れ条件を満たし、必須修正が解消している |

仕様が既に明示的に合意されている場合は、その根拠と適用範囲を記録して進めます。対象を動かせる状態にしてから判断を求め、沈黙やモックの完成を承認とみなしません。未合意の仕様に依存する本実装は進めず、調査・モックでの比較・独立した合意済み機能の作業を進めます。合意済みの期待結果を変更する場合は、理由と影響を提示して再合意します。

重要なケースはシナリオ ID と対応する自動テストに残します。実環境でしか確認できない項目は、実行条件と結果を記録して検証します。

<a id="boundaries"></a>
## 3. モックを作り込みすぎない

- 合意に必要な状態と遷移だけを再現し、業務ロジック、永続化、複雑な画面遷移をモック側に再実装しない。
- 本番と別の画面一式や、モック専用の汎用通信層を作らない。単純な固定データや既存の置換手段で足りるならそれを使う。
- シナリオ、データ定義、テストの対応を ID で追跡し、モックデータは本番の型・契約に合わせて一元管理する。契約が未確認の部分は仮定として残す。
- 新しいツールを採用する場合は、再現する境界・状態と、既存手段で不足する理由を示す。代表的なシナリオで試し、効果・設定や保守の負担・採用構成を設計の正本へ記録する。プロセスの導入を理由にツール一式を必須にしない。
- 実接続・本番構成ではモックを無効にする。実処理に失敗したときに、モックの応答やデータへ自動的に切り替えない。

## 4. 記録と実装への引き継ぎ

モック専用の仕様書・承認台帳は新設せず、既存の正本に次を集約します。

| 正本の記載箇所 | 残す内容 |
| --- | --- |
| 機能仕様 | シナリオ、期待結果、確認したモックの資産と版、合意の対象・判断者・日付・根拠 |
| 設計・実行手順 | モックの境界とデータの配置、起動・状態再現・終了・実処理への切り替え方法 |
| 検証結果 | シナリオに対応する実装・テスト、環境と対象版、モック確認と実処理検証それぞれの結果・証拠 |
| 作業計画 | 未決事項、依存範囲、未実装・未検証の状態と解消条件 |

モックでの確認は、外部仕様の正しさ、実際の保存・認証・性能・障害復旧を保証しません。対象機能に必要な確認は実処理で行い、実環境を利用できないなどの理由で未検証なら、該当する機能を完了扱いしません。再利用価値のあるモックは開発・回帰確認用に保持し、用途がなくなった資産だけを整理します。

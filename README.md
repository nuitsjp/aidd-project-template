# AIDD Project Template

配布版: **1**

オーバードキュメンテーションとオーバーエンジニアリングを抑え、動作するモックで仕様を確かめてから実処理へ接続するためのテンプレートです。ここでは、この進め方を「モック駆動開発」と呼びます。

言語、フレームワーク、画面の有無、保存方式、配置構成、開発ツールは固定しません。コピーするのは [template/](template/) の中身と [LICENSE](LICENSE) です。実行可能なアプリケーションや依存パッケージは含まず、各プロジェクトの要件に合わせて実装します。

## 1. 配布物と適用範囲

| コピーするファイル | 役割 |
| --- | --- |
| [README.md](template/README.md) | プロジェクトの入口と実行手順への案内 |
| [AGENTS.md](template/AGENTS.md) | エージェントが作業前後に参照する規則 |
| [PLAN.md](template/PLAN.md) | 作業状況、未決・未実装・未検証事項 |
| [docs/document-policy.md](template/docs/document-policy.md) | 採用版、適用範囲、情報ごとの正本、保護する合意 |
| [docs/project.md](template/docs/project.md) | プロジェクト固有の要件・仕様・設計・確認結果 |
| [docs/standards/design-and-documentation.md](template/docs/standards/design-and-documentation.md) | 文書と仕組みを増やす判断基準、検証と変更管理 |
| [docs/standards/mock-driven-development.md](template/docs/standards/mock-driven-development.md) | モック作成、仕様合意、実処理接続の手順 |

最初はプロジェクト固有の内容を `docs/project.md` にまとめます。機能仕様書、連携仕様書、設計書、用語集、設計判断記録は、分けて管理する必要が生じた時点で作成します。空の文書や図を一式そろえる必要はありません。

同梱の標準は、製品固有の要件・技術構成と分けて管理します。テンプレートの更新は、採用先への規約の自動適用を意味しません。本リポジトリーは [MIT ライセンス](LICENSE) で配布します。コピー時は著作権表示と許諾文も保持してください。

## 2. 新規プロジェクトにコピーする

このリポジトリーを clone または ZIP で取得し、ファイル管理ツールで `template/` の中身と `LICENSE` を新しいプロジェクトのルートへコピーします。以下は、取得したリポジトリーのルートから実行する PowerShell の例です。コピー先の `my-project` を実際の名前に変更してください。

```powershell
$templateSource = (Resolve-Path -LiteralPath './template').Path
$projectTarget = Join-Path (Split-Path -Parent (Get-Location).Path) 'my-project'
if (Test-Path -LiteralPath $projectTarget) {
    throw 'コピー先が存在します。新しい名前を指定するか、第4節の既存プロジェクト向け手順を使ってください。'
}
New-Item -ItemType Directory -Path $projectTarget | Out-Null
Get-ChildItem -LiteralPath $templateSource -Force | Copy-Item -Destination $projectTarget -Recurse
Copy-Item -LiteralPath './LICENSE' -Destination $projectTarget
Set-Location -LiteralPath $projectTarget
```

コピー後の文書はコピー先だけを参照します。配布元へのリンクや同期設定を追加する必要はありません。

## 3. 個別化して最初の機能を実装する

以下の順番で、最初の小さな機能を実処理まで通します。全機能の設計やモックの完成を待つ必要はありません。

| 順序 | 作業と記入先 | 次へ進める条件 |
| --- | --- | --- |
| 1 | `docs/document-policy.md` に採用記録、モックの適用範囲、既存規約との差分を記入する | 採用する規則とその範囲が確定している。適用状態を「適用済み」にする |
| 2 | `README.md` の名称・概要と、`docs/project.md` 第1・2節の目的、対象、対象外、制約、受け入れ条件を記入する | 最初に解決する問題と、実装しない範囲を説明できる |
| 3 | `docs/project.md` 第3・4節に最初の機能のシナリオ、外部仕様の確認根拠、実現する責務と境界を記入する。言語・ツールもこの機能に必要なものを選ぶ | 必要な事実と仮定を区別でき、期待結果を確かめる方法が決まっている |
| 4 | 対象機能に [モック駆動開発](template/docs/standards/mock-driven-development.md#workflow) を適用し、起動・状態再現の手順を `docs/project.md` 第5節へ記入する | 確認対象を動かせる状態で提示し、第3節に仕様合意を記録している |
| 5 | 合意した機能を実装し、必要な実処理へ接続する。実行・検証手順と結果を `docs/project.md` 第5・6節へ記入する | 必要な検証に合格している。モック適用時は、モックを無効にした環境でも期待結果が得られる |
| 6 | `PLAN.md` を更新し、差分を [完了基準](template/docs/standards/design-and-documentation.md#completion) と照合する | 残る未決・未検証を完了扱いせず、次の機能の範囲が分かる |

モック対象外の変更では、モックの作成と実処理への切り替えを省き、対象の変更に必要な通常の実装・検証へ進みます。文書のみの変更では、内容・リンク・合意との整合を確認して順序6へ進みます。仕様の判断待ちは、その仕様に依存する実装だけを止めます。既に明示された合意を記録し直すために再承認を求めません。

`{{...}}` は置換する記入欄です。未決の内容を推測で埋めず、`PLAN.md` に ID と解消条件を登録して、その参照に置き換えます。初期導入時点では、実行手順は「未実装」、確認結果は「未検証」と記入できます。それらを記入しただけで実装や検証が完了したことにはなりません。

個別化後に次のコマンドで記入欄の残りを確認できます。出力がなければ置換は済んでいます。内容の合意・実装・検証は上表の条件で別に確認します。

```powershell
Get-ChildItem -LiteralPath . -Recurse -File -Filter '*.md' |
    Select-String -Pattern '\{\{[^}]+\}\}'
```

初回導入は、採用範囲と最初の機能を具体化し、記入欄を解消した時点で完了です。機能の完了には順序5・6が必要です。以降は、機能ごとに順序3〜6を繰り返します。

## 4. 既存プロジェクトへ導入する

既存ファイルへ一括コピーせず、現在の要件・制約・文書配置と比較して必要な内容を取り込みます。

1. 現在の正本と保護する合意を確認し、テンプレートの各責務を既存のどのファイルが担うか対応付ける。既に仕様書があれば、その内容を `docs/project.md` へ複製しない。
2. 標準の追加・変更点を具体化する。既存の合意を変更する箇所は、変更前後・理由・影響を提示し、合意済みの範囲だけを取り込む。同名ファイルがある場合も上書きせず、別名で配置して参照先を合わせる。
3. 文書方針に標準 ID・版、適用開始日、対象範囲、差分と判断根拠、実際の正本のパスを記録し、`AGENTS.md` と入口文書のリンクを更新する。取り込む文書の著作権表示と許諾文も保持する。テンプレートの構成へ全面的に移行する必要はない。
4. 次に変更する小さな機能へ第3節の順序3〜6を適用する。既存機能すべてのモック化や、規約と無関係なリファクタリングを導入条件にしない。

## 5. 配布版の更新を取り込む

コピー先は独立して管理します。新版を自動適用せず、採用版と新版の規則を比較し、必要な変更だけを第4節と同じ手順で取り込みます。コピー先の製品要件、仕様、設計、合意記録、検証結果をテンプレートで置き換えません。取り込み後は採用版と差分を文書方針へ記録します。

## 6. 導入後に確認すること

- 決定事項ごとに正本が1箇所あり、リンクだけで辿れること。
- 採用した仕組みが現在の要件に対応し、不要な層・依存関係・文書を増やしていないこと。
- モックを使う機能では、シナリオと再現手順、確認した版、合意内容が対応していること。
- 実処理への切り替えを確認し、必要な実環境での検証結果と未検証範囲を区別していること。
- 既存の必須事項が無断で緩和されず、未決事項に依存する機能が完了扱いされていないこと。
